## Finding 1 — blocking, confirmed — `install.sh --uninstall --confirm` deleted files by an unsanitized manifest path (round 1, mkr-security-reviewer)

`run_uninstall()` iterated every key of `.claude/mkr-manifest` directly and ran `rm -f -- "$MKR_TARGET/$rel"` verbatim, with no validation that `$rel` stayed inside the paths install.sh could ever have written. `.claude/mkr-manifest` is an ordinary tracked file with no write-gate of its own, so a PR could append a line like `<hash> 644 ../../../../home/user/.ssh/authorized_keys`, or literally `CLAUDE.md`, and `--uninstall --confirm` would delete it — escaping `--target` or destroying the two files `docs/adr/0005` explicitly promises are never touched.

**Fix:** added `is_safe_owned_relpath()` (install.sh) — rejects any manifest-derived path that is absolute, contains a `..` or `.` path segment, or isn't rooted at `.claude/`/`.github/` (the only two directories `install.sh` ever enumerates). `run_uninstall()` now filters every candidate through it before adding it to the deletion set; a rejected entry is skipped with a stderr WARN naming it, not silently dropped.

**Independently verified:** hand-traced the function against a dozen constructed traversal strings (leading, middle, and trailing `..` segments; bare `.claude`; `.claude/./foo`) via a standalone shell invocation — all correctly rejected, all legitimate `.claude/`/`.github/` paths correctly accepted. `tests/install_test.sh`'s new `G4-fix` case plants both a path-traversal entry (pointing at a canary file outside `--target`) and a literal `CLAUDE.md` entry in a real manifest, runs `--uninstall --confirm`, and asserts both survive untouched while a legitimate entry is still actually removed — a real regression test, not a placebo.

## Finding 2 — blocking, plausible → became a real, worse defect on fix — `id-collision-guard.sh`'s new `origin/main` fetch could hang, and its fix introduced argument injection (round 1 + round 2, mkr-security-reviewer)

Round 1: the best-effort `git fetch` bounding a slow/unreachable remote depended entirely on the `timeout` binary being on `PATH`; the fallback path (no `timeout`) ran the fetch completely unbounded, contradicting the file's own "fails open, never blocks" design — a session-wide hang on any machine lacking `timeout` (e.g. stock macOS) against a slow or adversarial `origin`.

Round 1 fix (first pass): skip the live fetch entirely when `timeout` is absent — no fallback fetch at all, only whatever `origin/<branch>` ref is already cached locally. Also generalized the hardcoded `origin/main` to `origin/<first entry of MKR_PROTECTED_BRANCHES>` (reused elsewhere in this codebase, e.g. `mkr-code-review`'s own branch resolution), matching a non-blocking suggestion from round 1's mkr-code-reviewer.

**Round 2 found the fix introduced a new, more severe defect:** the new `default_branch` (from `MKR_PROTECTED_BRANCHES`, read from the checked-out, PR-controlled `.mkr/config`) was passed as a bare positional argument to `git fetch --quiet --no-tags origin "$default_branch"`. Since `git fetch` permutes options anywhere in argv, an option-shaped value such as `MKR_PROTECTED_BRANCHES="--upload-pack=<program>"` would be read as a real fetch option — a program of the attacker's choosing invoked as the upload-pack service — not a literal branch name. Reachable via any ordinary `Write` to an ADR/`MKR_ID_DIRS` path on a branch carrying the crafted config, no special privilege needed.

**Fix:** added `--` before `"$default_branch"` in the `git fetch` call — git's standard end-of-options marker, honored by `fetch`'s `parse-options` handling. The other two uses of `$default_branch` in the same file (`"origin/$default_branch"`, embedded inside a literal prefix that can never itself start with `-`) were confirmed already safe and left untouched.

**Independently verified, twice.** First, by hand: built a real bare-repo remote and a small marker script, then ran `git fetch --quiet --no-tags origin "--upload-pack=<script>"` (no `--`) and confirmed the script actually ran (marker file created); re-ran with `--` inserted and confirmed it correctly failed as an invalid-refspec error, marker never created. Second, by a proper regression test (`tests/hooks_test.sh`'s `G9`): the first draft of this test used a payload containing a literal space (`"--upload-pack=touch <marker>"`), which `mkr_list()`'s own `IFS=' '` space-splitting silently truncated before it ever reached `git fetch` — both round-3 reviewers (independently, same round) caught that the test would pass identically whether the `--` fix was present or reverted, proving nothing. Rebuilt as a single space-free token (a marker script's own path, matching what a real `--upload-pack=<program>` value looks like) — this session then confirmed by direct mutation: reverting the `--` fix makes `G9` fail (`marker_exists=yes`); restoring it makes `G9` pass. A real, mutation-resistant regression guard, not a placebo (CLAUDE.md's own bar for this file: "a passing case that a targeted mutation wouldn't also fail proves nothing").

## Finding 3 — blocking, confirmed — `mkr-code-reviewer`'s new Boundaries/Seams check was unimplementable (round 1, mkr-code-reviewer)

The check told `mkr-code-reviewer` (tools: `Read, Grep, Glob` only, no `Bash`) to itself run `config.sh list MKR_BOUNDARIES` — impossible for a tool-less agent. `mkr-code-review/SKILL.md` (which does have shell access, and already resolves `MKR_REVIEWS_DIR` for exactly this reason) was never updated to resolve `MKR_BOUNDARIES` and pass it in, unlike the correct pattern this same diff used for `MKR_SPEC_EXTRA_SECTIONS` in `mkr-spec-reviewer`.

**Fix:** `mkr-code-review/SKILL.md` step 2 now resolves `MKR_BOUNDARIES` (`config.sh list`, CLI mode) alongside `MKR_REVIEWS_DIR`, and step 4 passes it to the spawned agent(s). `mkr-code-reviewer.md`'s "Inputs you will be given" now lists it as a given input, and check 6's text says "use the value you were given" rather than instructing the agent to fetch it. `specs/M2_CodeReview_Spec.md`'s data-model row was corrected to match (consumed by `mkr-code-review`, not `mkr-code-reviewer` directly).

**Independently verified:** read both files directly, confirmed the old imperative "Read `config.sh list MKR_BOUNDARIES`" phrasing is gone from the agent file and the skill genuinely resolves + passes it, mirroring `mkr-spec-review`'s already-correct handling of `MKR_SPEC_EXTRA_SECTIONS` side by side.

## Verification discipline

Every blocking finding above was independently reproduced by this session, not accepted on either reviewer's prose alone: the path-traversal fix was hand-tested against constructed adversarial strings and covered by a real deletion-attempt test; the argument-injection fix was hand-exploited against a real git remote and script (confirmed both the vulnerability and the fix work as described) and is now covered by a mutation-verified regression test (confirmed to fail against the reverted code, pass against the fixed code); the Boundaries/Seams fix was confirmed by reading both files side by side against the already-correct `MKR_SPEC_EXTRA_SECTIONS` pattern.

Round 3's two agent instances converged independently on the same conclusion (the underlying `--` fix is sound; only the `G9` test's payload construction was flawed) — this session fixed that flaw and verified it directly via mutation testing rather than spawning a fourth agent round, since the remaining question ("does this specific test now catch a regression of this specific fix") is more reliably answered by literally reverting the fix and watching the test fail than by another round of code-reading judgment. All four suites (`config_test.sh`, `hooks_test.sh`, `install_test.sh`, `mkr_artifact_test.sh`) were re-run after every commit in this sequence; the only failures throughout are `config_test.sh`'s three pre-existing `TC-06c` cases (root-user sandbox artifact — `chmod 000` doesn't block root reads — reproduced identically against a pristine clone of `main`, unrelated to this diff).
